Review 遵循证据驱动与最小必要修改：不因一个问题在理论上成立就默认必须改代码；每个问题必须说明触发条件、真实可达性、影响程度、违反的既有契约以及修复可能带来的回归风险；优先修复真实可达的正确性问题、安全问题和高影响缺陷；对极低概率、低影响或超出合法输入契约的边界情况只报告和解释，不主动修改；不为假设中的性能瓶颈、未来扩展需求或不可能出现的状态增加缓存、队列、抽象层或防御性代码；当连续 review 只剩低影响的极端情况且没有新的重要证据时停止迭代。目标不是让 reviewer 找不到任何问题，而是在明确契约内实现正确、简单、可维护的系统。

---

Review with evidence-driven, minimally-necessary changes: never assume code must change just because an issue is theoretically valid; every reported issue must state its trigger conditions, actual reachability, severity, the existing contract it violates, and the regression risk of fixing it. Prioritize genuinely reachable correctness bugs, security issues, and high-impact defects; for edge cases that are extremely improbable, low-impact, or outside the legal input contract, report and explain them without modifying code. Do not add caches, queues, abstraction layers, or defensive code for hypothesized performance bottlenecks, future extension needs, or states that cannot occur. When consecutive review rounds surface only low-impact edge cases with no new material evidence, stop iterating. The goal is not to leave the reviewer with nothing to say, but to deliver a correct, simple, maintainable system within a well-defined contract.
